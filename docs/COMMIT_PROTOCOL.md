# Commit and publication protocol

The packet validates its current contract and concrete action before acquiring the evidence-file lock. A publisher can change the authoritative files after that validation and before the event bytes are appended. The packet lock is an in-process RLock keyed by the event file; publishers do not acquire it. There is no single linearization point tying the validated model to publication and paired evidence. The observable race window starts when the last relevant contract read/check finishes and ends when the event record is appended. Appending the validation record introduces a second visibility point. Packet exception rollback truncates its two files, but process death can interrupt the pair and cross-process writers do not share its lock.

## Opt-in cooperative mode

Set server GuardConfig `publication_protocol="cooperative"`. Default `packet` behavior remains available for the baseline. Initialize each project with `python tools/publish_project.py --project <project-directory> --initialize`. For updates, prepare a complete separate project directory with the same project ID and run `python tools/publish_project.py --project <live-directory> --staged-project <staged-directory>`. The command runs native loader validation and Gate 0 before exposing the staged bytes and validates again before the marker flip. The lower-level publication API accepts an explicit validation callback; experimental malformed fixtures are not silently asserted to have passed Gate 0.

A per-project `.publication.lock` combines a thread RLock with a kernel advisory lock: a one-byte msvcrt lock on Windows or flock on POSIX. A thread can re-enter it. All cooperating backend processes must resolve the same project path. Publishers hold this lock while replacing projections and while replacing `.publication.json` last. This stronger-than-minimum lock duration also excludes a commit during in-place publication. Each individual replacement is same-directory temporary-file write, flush, fsync, and atomic replace. Windows sharing violations are retried for at most five seconds because a simultaneous reader can briefly prevent replacement. Exhaustion leaves an explicit failure, not a silently non-atomic write.

The marker contains a positive integer generation and SHA-256 hashes of the deployment and prompt projections. The next publisher reads the marker under the lock and increments its generation. It publishes instance, trace, agents, room plan, metadata, optional standalone placement, and KB documents. It never publishes runtime evidence or lock/journal files as projections. Project-local paths are required. Publication is not a multi-file atomic filesystem operation: an interrupted deployment can leave mixed files, and the marker still denotes the prior generation. Its recovery is a complete republication, not an automatic restoration of old model bytes.

The consistent loader reads the marker, hashes every manifested file, loads and validates the native contract, hashes every file again, and rereads the marker. It retries a changed marker up to three times and otherwise refuses missing, invalid, or mismatching projections with `E_PUBLICATION_INCONSISTENT`. An unchanged generation counter alone would miss a publisher stopped before its last flip; the manifest checks close that case. KB inventory is also checked. Cooperative setup holds the project lock across room plan, agents, KB, contract loading, and session creation so separately read projections cannot straddle publications. Files not in the declared deployment/prompt projection set are not covered.

A session retains the publication generation and executable fingerprint. In cooperative `log_backend_events`, the same project lock encloses the entire authoritative reload, generation and fingerprint comparisons, exact-action comparison, and recoverable append. The generation must match the session pin even when a chosen fingerprint slice is unchanged. The publisher cannot flip the marker between comparison and append. Session mutations are hidden from another HTTP turn by a per-session lock until commit or restoration. A client re-pin creates a new session; preserving conversation history across a new model has not been evaluated.

## Evidence journal and visibility

The cooperative append records original byte lengths of both evidence files in `.evidence-transaction.json`, atomically replaces and fsyncs that undo intent before touching either log, writes and fsyncs each payload, and removes the intent after both are complete. With a valid pre-existing log, recovery under the project lock truncates both logs to their recorded lengths whenever an intent exists. Recovery is idempotent if interrupted during truncation. An invalid journal or a log shorter than its recorded starting length refuses later commits as `E_EVIDENCE_APPEND`; it is not discarded as though recovery succeeded.

The commit linearization point for this interface is removal of the undo intent, under the project lock, after both payloads have been fsynced. Publication linearizes at atomic marker replacement under that same lock. `read_evidence_pair` takes the project lock and recovers before reading; this is the interface through which all-or-nothing pair visibility is claimed. An unlocked reader of the raw JSONL files can see the first append while the second is incomplete. The implementation does not claim simultaneous visibility of two ordinary files to arbitrary filesystem readers.

A killed backend can die after the pair commits but before responding to the caller. The durable pair remains while the client lacks an acknowledgement. There is no client idempotency key or exactly-once retry guarantee. Diagnostic exception hooks after the commit point do not uncommit a pair; process termination there demonstrates the acknowledgement gap. The in-memory session store is not durable: process death loses sessions, even when evidence has committed. A new session is required after restart.

## Restore failures and external effects

The original restore method assigned history, agent histories, active agent, and timestamp in sequence. Injected exceptions exposed partially restored states. The coordinated fix prepares deep copies and conversions in a new attribute dictionary and replaces the session object's dictionary in one assignment under the session lock. This preserves references to the SessionState object. Preparation failure leaves the entire pre-restore state, and a failure after replacement leaves the entire restored state; retry is safe. This is a Python in-memory atomicity argument under cooperative threads, not persistence across process termination. The raw pre-fix results and post-fix fault results are retained separately.

The first local sink file demonstrates persistence; the separate append-only increment-sink test (`experiments/commit_effects.py`) performs a non-idempotent effect before a forced commit rejection; restoring conversation state does not undo the sink. The test-only ordering that emits the effect only after a successful commit suppresses it on rejection. A crash after commit but before delivery can still lose that effect, and a retried delivery can duplicate it. A transactional outbox and idempotent receiver would be additional mechanisms; neither is implemented or claimed here. General backend operations with remote, non-idempotent effects are outside the demonstrated rollback scope.

## Direct edits and assumptions

The guarantee requires publishers, evidence writers/readers, and all backend processes to use the shared protocol. Atomic replacement must have local-filesystem semantics, fsync must behave as advertised, and deployment paths must remain stable. Network filesystem lock behavior, storage corruption, adversarial modification of lock/journal files, OS failure, and power loss are not covered by the process-kill experiments. Python has no portable Windows directory fsync, so power-loss durability of marker/journal directory entries is specifically not claimed. Linux flock is implemented but has not been executed on this Windows host. Processes must use spawn or start before publication/commit critical sections; forking while holding the project lock is not supported or evaluated.

Direct editing after a commit comparison can change a projection before evidence becomes visible without acquiring the lock or advancing the marker. Generation-only checks cannot observe this. The forced direct-edit test records this residual revision mismatch and the next consistent load's refusal. Editing during a generation/read/re-read sequence can also exploit arbitrary ABA rewrites; the cooperative-publisher assumption excludes them. The protocol detects stable direct edits at the next loader check, not every possible direct edit at the instant it happens.

## Executed scope variants

`commit_variant` selects `none`, `digest_only` (F0), `full` (F1), `slice` (F2), or `slice_prompt` (F3). Full is the default packet executable fingerprint. None uses the pinned descriptor without an authoritative reload in packet mode. Digest-only hashes the pinned instance serialization; it deliberately ignores trace and prompt edits and bypasses full loader revalidation at commit. F2 hashes the Gate-0 canonical all-pairs routing table plus the complete declared runtime-action set including schemas. F3 adds selected agent prompt fields and KB document hashes. The Gate-0 verifier is same-author code, so its table is not an independent oracle. Each scoped commit still compares the concrete admitted action, except intentionally weakened none/digest-only variants. The separate reach-only experiment uses explicit unbound validation evidence with no fabricated model assertion.

Full pre-call revalidation remains enabled in all commit-scope variants. These ablations isolate commit behavior; they do not replace every pre-call check with a slice. A between-turn executable change already costs zero model calls in the packet when preflight detects it. The optional generation check can reject a changed generation even when F1 considers its files equivalent, but is not claimed to eliminate wasted calls that preflight already prevents. During generation, relevant publication can still waste the completed model call before a rejected commit.

Strict cooperative generation equality means every publication invalidates old pins, including a routing-equivalent publication. F2 cannot improve that strict protocol's admission availability merely by ignoring a fingerprint change. Packet scope-only storm cells show the separately weakened comparison behavior. Revalidation additionally checks structural consistency, trace/schema/action paths, declared hashes and placement projections; a model-digest comparison alone cannot establish those properties after a trace or projection edit. Prompt integrity is scoped separately from routing and is not a defense against arbitrary prompt injection.

## Evidence and remaining scope

`verification/interleavings.py` exhaustively counts schedules in an explicit-state abstraction with one/two publishers, one/two sessions, five projection writes, publication flip, snapshot/read/validate/lock/compare/append/unlock/restore steps. It is not a proof of Python or OS implementation. Generation mismatch and direct-edit revision mismatch are distinguished in traces. `experiments/commit_stress.py` uses actual SessionStore calls and the production logger, 50 simultaneous scripted generations per cell, thread and five-process execution, and full/slice scopes. `experiments/commit_faults.py` kills child processes externally and tests append exceptions, partial writes, all publication prefixes, actual session restoration, and a local side-effect sink. `experiments/commit_restore_faults.py` separately evaluates the atomic restore fix. `experiments/commit_scopes.py` records synthetic scope edits and pre-call checks.

Every evaluation gets an immutable raw directory with script and production source hashes taken before it starts. Interrupted runs remain present. The stress workload intentionally waits until every session has entered its scripted model call before the first republication; its abort rates are workload observations, not deployment frequencies. The natural WP5 evolution corpus, independent edit labels, real-model concurrency run, and migration across re-pin are not supplied by these offline experiments. Synthetic labels currently come from the same-author Gate-0 table and cannot support an independence claim. Generated result tables must retain these limits and distinguish pre-fix, interrupted, and complete runs.

The final monitored stress run compares every projection byte hash with the current manifest at append. For cooperative commits this monitor runs under the project lock, independently of the loader verification. Its reported quantity is append-time manifest mismatches among monitored commits, not an unbounded proof that no torn read is possible. Packet observations run without publisher exclusion and can be unavailable because a Windows file replacement denies the diagnostic read; observer failures are recorded without changing the transaction outcome. The earlier monitored attempt that threw diagnostic errors is retained as an interrupted harness run.
