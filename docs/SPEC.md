# SPEC v1


This section is the **normative specification** of the guard (version SPEC v1). It describes what the guard is supposed to do, independent of how the packet's code does it. Where the code disagrees with this text, that is a finding (section 6.5), not a reason to edit the text silently.

**4.1 Model and declaration path.** A session is pinned to one instance of the model, identified by the SHA-256 digest of its serialization. The model declares scene objects, the object groups and zones they belong to, and agents with the objects, groups, and zones they are responsible for and the agents they may hand over to. It also declares which runtime action realizes the answering capability for a given agent and object. An operation is reachable only through the path `s -> u -> c -> b -> a`: a scenario step `s` names a capability use `u`; `u` fixes provider and target and resolves exactly one capability `c`, one runtime binding `b`, one action `a`. A step never calls an action directly.

**4.2 Responsibility resolution.** For a target object `t`, `R(t)` is the set of owners at the **most specific level that has any owner**: asset level if non-empty, else group level if non-empty, else zone level. **Exactly one provider must remain at the deciding level.** If that level names several agents, reject; do not fall through to a less specific level that happens to have a unique owner. If no level names an owner, reject. A group or zone expresses shared responsibility; an owner of a single object overrides it for that object. This is a deterministic specificity policy, not a model of whom a visitor expects to answer.

**4.3 Admission.** A request is admitted only if all five conditions hold, checked in this order, and the first failing condition determines the reason:
1. The session is pinned to a model whose digest matches the request. (The request is compared with the session's own pin, not with the currently published model.)
2. Entity and source identifiers resolve to the same unique target, in a resolved, unambiguous selection state (`none` and `ambiguous` are rejected; a set ambiguity flag and a contradicting candidate list are rejected).
3. `R(t)` yields exactly one provider `p`, and `p` is the active agent or is reachable by one declared handoff (`max_handoffs` is 1).
4. Exactly one capability use resolves to exactly one capability, binding, and action for `(p, t)`.
5. The request satisfies the action's declared schema.
A failed condition produces a specific rejection **before any language-model call and before any state is touched**. Outcomes: `ANSWER_LOCAL` (p equals the active agent), `ANSWER_AFTER_HANDOFF` (one declared edge from the active agent to p), `REJECT(reason)`.

**4.4 Commit and re-pin.** Before generation the backend snapshots the mutable session state. The language model's output is constrained by a schema whose handoff field accepts only declared handoff targets, which for a grounded turn is the empty set; if constrained decoding is unavailable the system falls back to unconstrained JSON and the backend checks the output itself: a turn whose output names a handoff is aborted and the snapshot restored (a deployment may instead drop the field and log it). A turn commits only after the model is validated again: reload from the authoritative source, validate, compare the fingerprint with the one taken at admission, require the preselected action to appear exactly once in the reloaded context, append the evidence records atomically, and on any failure restore the snapshot. The fingerprint covers digest, trace, and runtime context and excludes descriptive metadata. After a rollback caused by a changed model the client **re-pins**: it opens a new session on the currently published model; setup validates the published files again and refuses if they are inconsistent; a re-pinned session starts a fresh conversation.

**4.5 Guarantees (if a turn commits).** (G1) its target was resolved from the pinned model; (G2) exactly one provider decided, at most one declared handoff away from the active agent *as reported for the request*; (G3) the operation is the single one the model declares for that provider and target; (G4) at the commit check the executable contract equals the one at admission; (G5) no routing decision other than the derived one took effect, so a handoff proposed by the language model never does. **Not guaranteed**: that the visitor meant the selected object; that the answer is correct or concerns the selected object; that a redirection written into the answer text is absent; that persona text is unchanged unless it is part of the fingerprint; that the published model assigns responsibility sensibly; compensation for external side effects (the snapshot restores only in-memory session state).

**4.6 Threat model.** Client and language model are untrusted. The client supplies digest, entity and source identifiers, geometry, and the active agent. The language model supplies answer text and may supply a routing proposal. The authoring pipeline is trusted to publish consistent files but not to publish a sensible model. Backend, loader, and published files are the trusted computing base. The provider is always derived, never taken from the client. The active agent is reported by the client in the packet's code, so G2 holds only relative to that report; the visitor chooses whom to address, which is application semantics. Section 7 (WP3) adds an optional server-tracked active agent.

**4.7 Design choices to be tested, not assumed**: the one-handoff limit; exactly one provider at the deciding level; fail closed instead of falling back to a plausible agent; abort versus drop-and-log for handoff proposals; global fingerprint versus a routing-relevant slice; derive versus ask.

**4.8 Publish-time verification.** Model-only ownership, reachability and declared-path properties can be verified when the model is published. The new design therefore has **Gate 0 (publish-time verification)**: all routing semantics are checked once per published model and a canonical routing table (every `(start agent, scene object)` pair with decision, reason, provider, and declared action) is computed and indexed by the digest. Gates 1 to 3 at runtime are lookups in that verified table plus the request-bound checks that only exist at runtime (stale digest, forged or contradicting identifiers, selection state, active agent, schema). Table lookup and runtime derivation are compared for model-only properties; request-bound checks remain distinct.


## Data-format appendix (factual encoding, inspected before implementation)

The supplied native instance is a JSON object. Its "objects" list contains records with unique "id" and "type". References are lists of record IDs. The instance schema is supplied separately as data; readers must parse the instance independently.

- Agents have type "Agent", kind "agent", entityRole "interactiveAgent", an entity ID in "id", and the wire-level agent ID in "sourceAgentId" (also present as "sourceId"). Responsibility references are "groundedAsset", "groundedObjectGroup", and "responsibleZone"; permitted handoff references are "handoffTarget".
- Scene objects have type "Entity", kind "asset", entityRole "sceneObject"; "sourceId" is the wire object ID, "objectGroup" lists group entity IDs, and "sourceGroup" is a descriptive label.
- Group entities have type "Entity", kind "asset", entityRole "objectGroup". Zone entities have kind "zone", entityRole "semanticZone". Their "sourceObjectId" lists contain wire source IDs. Group membership is also explicitly carried by a scene object's "objectGroup".
- "ScenarioStep.capabilityUse" references CapabilityUse records. A CapabilityUse has "provider" and "target" reference lists and "typeRef" containing its Capability ID.
- RuntimeBinding records have "capability" and "runtimeAction" reference lists. RuntimeAction has "locator", "inputSchema", and "outputSchema" references. RuntimeActionLocator records carry kind and value. SchemaReference records carry JSON schemas as JSON-encoded strings in "text" with uri "json".
- trace_map.v2.json is a derived projection. Its "runtime_actions" entries contain "action_kind", "scenario_step_id", "capability_use_id", "capability_id", "provider_entity_id", "target_ids", "runtime_binding_id", "runtime_action_id", and "locator". Answering entries have action_kind "chat" and endpoint "POST /chat". Infrastructure and handoff entries also exist and must not be mistaken for answering operations.
- The chat input schema in the example requires session_id, active_agent_id, user_text, and interaction_mode. For interaction_mode "deictic" it requires spatial_context. spatial_context requires model_sha256, state ("resolved"), hit_position {x,y,z}, distance_m, and selection_modality. Identity fields are entity_id and source_object_id (alias source_id). Candidate and ambiguity fields are candidate_entity_ids, ambiguous, ambiguity, and ambiguity_reason. The schema permits entity-only or source-only identity forms. This appendix reports the schema; specification ambiguities should be reported instead of silently resolved.
- The example trace records model_sha256 as uppercase hex; project metadata records roomcontract_model_sha256. SPEC v1 describes a serialization digest but does not yet fix a portable serialization normalization scheme.
- Input declarations may include modelBinding metadata. The trace projection alone is not the model's declaration path: the referenced records and their links remain available to independently verify the path.

## Independent evaluator interchange

This interface names inputs and outputs without defining additional decision semantics. Implement evaluate(instance, trace, request, session) returning a JSON-serializable mapping with keys decision, reason, provider, action. decision is ANSWER_LOCAL, ANSWER_AFTER_HANDOFF, or REJECT. For admitted turns reason is null, provider is the wire sourceAgentId, and action is the declared RuntimeAction ID; for rejection use null for provider and action. session contains model_sha256 and optionally active_agent_mode ("client" or "server_strict") and active_agent_id. request is the declared chat wire-format request. The initial task concerns admission only; commit is a separate stateful evaluation.

Reason vocabulary: E_STALE_DIGEST, E_UNKNOWN_ENTITY, E_ID_MISMATCH, E_SELECTION_STATE, E_UNOWNED, E_AMBIGUOUS_OWNER, E_NO_HANDOFF_PATH, E_NO_DECLARED_ACTION, E_ACTION_AMBIGUOUS, E_SCHEMA, E_ACTIVE_AGENT_UNKNOWN, E_ACTIVE_AGENT_MISMATCH, E_PUBLICATION_INCONSISTENT. Record uncertain ordering or unspecified meanings as ambiguities. Do not infer unspecified behavior from other software. Handwritten fixtures are small semantic examples, not claimed to be complete authoring-valid models.
